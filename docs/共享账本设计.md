# 共享账本设计（云共创）

目标：像 Google Sheets / 金山文档那样，**一个账本多人共记共看**。
家庭或小团体各自用自己的账号登录，谁记的都能看到。

## 1. 数据模型

```ts
AccountBook {
  accountBookId, accountBookName,
  ownerId: number,          // 创建者
  members: number[],        // 成员 userId 列表
  inviteCode?: string,      // 6 位邀请码，可重置
  type: 'private' | 'shared'
}

BookMember {                // 服务端表 book_members
  bookId, userId, role: 'owner' | 'member', joinedAt
}
```

服务端 `records` 表加一列 `book_id`，推送时从 payload 取，便于按账本授权。

## 2. 邀请方式（先做邀请码，不做邮件）

- 账本设置页 → 「邀请成员」→ 生成 6 位码（如 `X7K2M9`），24 小时有效
- 对方在「加入账本」输入码 → 成为 member
- 不做邮件邀请：省一套邮件服务，且中国用户未必查邮件

## 3. 权限（默认值，可改）

| 操作 | owner | member |
|---|---|---|
| 查看本账本全部记录 | ✅ | ✅ |
| 新增记录 | ✅ | ✅ |
| 修改/删除**自己的**记录 | ✅ | ✅ |
| 修改/删除**他人的**记录 | ✅ | ❌（只读） |
| 邀请/移除成员 | ✅ | ❌ |
| 删除账本 | ✅ | ❌ |

理由：记账是"我的数据"，别人改我的会引发信任问题。这条要保留。

## 4. ★ 核心技术问题：ID 冲突

现在 `billId` 是**秒级时间戳**。两个成员在同一秒记账 → 撞 ID → 同步后合并成一条，数据丢失。

三种解法：

| 方案 | 做法 | 评价 |
|---|---|---|
| A. 复合键 | 本地键改成 `ownerId:billId` | 干净，但要改所有按 billId 的查找 |
| B. 拉取时重编号 | 外来记录若与本地冲突，billId += 1 直到不冲突 | 简单，但每次同步结果不稳定 |
| C. 服务端分配 ID | 推送时由服务端生成全局唯一 id | 最正确，但要改离线优先的逻辑 |

**我建议 A**：给 Bill 加 `ownerId`，本地存储与同步都用 `ownerId:billId` 作为键，显示时照常用 billId。
一次性重构，之后一劳永逸。

## 5. 展示

- 账单行显示头像色块（邮箱首字母）+ 昵称
- 账本切换器里，共享账本带「共享」标记和成员数
- 顶部显示「3 人共记」

## 6. 同步

- `pull` 返回：我自己账本的全部记录 + **我参与的共享账本里所有成员**的记录
- `push` 校验：写入的 bookId 必须是我参与的账本
- 冲突维持 last-write-wins（按 record.updateTime）

## 7. 退出与删除

- member 退出：其历史记录**保留在账本**（归属不变），只是不再同步新数据
- owner 删除账本：所有成员的本地副本收到删除墓碑
- 成员数据迁移：加入前我的私有账本不受影响

## 8. 实现顺序

1. 服务端：`books` / `book_members` 表 + 记录按账本授权
2. 客户端：BookMember 模型 + `ownerId:billId` 复合键重构
3. 界面：邀请码 / 加入账本 / 成员列表 / 共享标记
4. 账单归属展示
