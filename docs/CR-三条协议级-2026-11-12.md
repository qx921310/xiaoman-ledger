# CR：版本协议 / 账本代次 / 会话隔离（2026-11-12）

审阅对象：Codex 提交 `ba2ee83`（及 `e9155e5` 之上的 v2 协议实现）。
方法：读代码定位 + 假 adapter 精确复现（`tests/cr-sync-v2.test.ts`），不依赖网络与生产数据。
样本：固定场景逐条验证；涉及统计的判断另见既有 1500 样本并发压测。

## 一、结论

三条协议方向正确，实现基本到位：服务端 CAS（`baseVersion` + `revision`）、操作幂等（`operationId` + `sync_operations`）、账本代次（`generation`）、会话代次（`AbortController` + `navigator.locks`）都已落地，并配有冲突留存与人工核对入口。

**但有 1 个 P0 级可用性缺陷、3 个 P1 缺陷、若干边界未覆盖**，建议修完再验收。

| 级别 | 问题 | 证据 |
|---|---|---|
| **P0** | 任何一条冲突会**冻结整个账号的所有推送** | 已复现：1 条冲突时推送条数 = 0 |
| P1 | `sync_operations` 无清理策略，无限增长 | 代码：仅 INSERT，无 DELETE |
| P1 | 无 bookId 的实体不走代次校验，共享账本多人不可见 | 代码：`if (bookId)` 才校验 generation |
| P1 | 冲突冻结后无「忽略/放弃本地版本」出口，只有「保留本地重试」 | 设置页仅 `keepLocalConflict` |
| P2 | `sync-v2-state` 的冲突文案是内部状态码直出 | `同步未完成：${receipt.status}` |

## 二、P0：一条冲突冻结全账号同步

位置：`src/domain/sync-v2-runner.ts:57`

```ts
const pending = Object.keys(meta.conflicts).length ? [] : Object.entries(meta.pending)
```

**复现**（`tests/run-cr-sync-v2.cjs` 第 1 项）：

```
1 条历史冲突 + 1 条待推送记录 → 实际推送条数 = 0
```

**影响**：

- 用户只要有**一条**记录进入冲突（例如换设备后一条被服务端附加字段的记录），此后**所有新记账都不再上传**，且界面只会显示「N 条待处理」。
- 两人协作时，任一方制造冲突就可能让**整个账本**停止同步，且不会自愈。
- 冲突原因若是「账本代次未知」这类可自愈情形，也会永久卡住。

**建议**（二选一）：

1. **按记录隔离**：冲突只停该 key，其余 pending 照常推送（改 `pending` 过滤，而不是整体置空）。
2. **保留全局冻结但强制出口**：冻结时必须有显眼的「导出并忽略冲突」「放弃本地版本」操作，且 24h 未处理时自动降级为按记录隔离。

**验收**：冲突 1 条 + pending 5 条 → 至少 4 条成功推送；冲突记录保持待核对；重试不会反复制造新冲突。

## 三、P1：操作幂等表无清理

位置：`server/server.mjs:647,706`

```sql
INSERT INTO sync_operations(user_id, operation_id, fingerprint, result) ...
```

只写不删。每条待推送记录产生一行，长期使用会持续膨胀（每次本地改动一条）。手机长期使用 + 频繁同步后表会到十万级，查询虽有主键但磁盘与备份体积会明显增长。

**建议**：按时间或条数保留（例如保留最近 7 天或每用户最近 5 万条），在 push 结束时按概率触发清理；清理不得影响重试窗口（客户端重试都在分钟级）。

**验收**：插入 10 万行后清理生效；7 天内的重试仍命中原结果。

## 四、P1：无 bookId 的实体不受代次保护

位置：`server/server.mjs:653`（`if (bookId)` 才校验 generation）

`splitGroup` / `splitMember` / `template` / `homeLoan` / `instalment` / `stockAsset` 等实体本身没有 bookId 时，走个人作用域：既不参与共享账本同步，也不受清空代次约束。后果：

- 共享账本里两人**看不到彼此的模板/AA/持仓**；
- 清空账本后这些实体仍可上传（与 CR-4 复现 A 同源）。

**建议**：明确实体归属矩阵（哪些必须 book 作用域），在 v2 协议里对必须归属的 kind 强制 `book-required`（现在只覆盖 `bill/transfer/lend/refund/reimbursement/cycle`），并在客户端创建时写入 `bookId`。

**验收**：两人账本下，A 建模板/AA/持仓 → B 可见；清空后旧代次上传被拒并转冲突。

## 五、P1：冲突只有「保留本地」一个出口

位置：`src/features/settings.tsx`（`keepLocalConflict`）

用户只能选「用我的版本覆盖云端」。缺：

- 「用云端版本」（放弃本地）；
- 「两条都留」（本地另存为新记录）；
- 「暂时忽略」（把该 key 移出冲突，保持待推送并持续重试）。

没有这些出口时，P0 的冻结就变成死锁。

## 六、已确认无问题（避免误伤）

- **指纹键顺序无关**：`sync-v2-state.ts` 的 `fingerprint` 对键排序，重试安全（已验证）。
- **`stale-generation` 转冲突而非静默丢弃**：已复现，冲突数 = 1。
- **`advanceSessionEpoch` 在登录与登出两处调用**：`App.tsx:32,123`，在途请求会被 abort。
- **同步串行**：`navigator.locks` + `inFlight` 按会话复用，避免并发写 outbox。
- **WAL + 在线备份**：`.backup` 已替换裸拷贝。

## 七、建议的回归清单

| 场景 | 期望 |
|---|---|
| 1 条冲突 + N 条 pending | 其余 N 条正常推送（P0 修复后） |
| 冲突处理三种出口 | 各自结果可预期，且不产生新冲突 |
| 10 万条操作记录 | 清理后仍能命重试窗口 |
| 两人账本：模板/AA/持仓 | 双方可见、可删、删除有墓碑 |
| 清空后旧代次上传（含未上传离线记录、未来时钟） | 一律转冲突，不静默复活 |
| 切换账号时有在途推送 | 旧请求 abort，结果不落到新账号 |
| 连续 100 次本地改动 | 合并推送 + 无自循环（已具备） |

## 八、优先级建议

1. **先修 P0**（冲突按记录隔离 或 强制出口）——不修则冲突一次即长期停同步。
2. 再补 P1 的三项（操作表清理、实体归属矩阵、冲突出口）。
3. P2 文案改为用户语言（「账本已清空，这条是清空前的旧记录」）。

> 说明：本 CR 未在真机双设备、生产数据上验证；结论基于代码与隔离复现。
