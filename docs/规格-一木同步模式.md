# 一木同步模式规格（逆向证据版）

> 依据：`research/yimubill/apk-dec/res/layout/` 下的 `dialog_data_sync_all.xml`、`dialog_data_sync_download.xml`、`fragment_my.xml`、`activity_backup.xml`。
> 目的：替换我们现有的「冲突保留本地 + 反复提示」设计，改成与一木一致的「云端为准 + 显式数据修复」。

## 一、日常同步（默认行为）

```
方向     以云端为准的增量同步
冲突     不逐条弹窗、不长期保留「待核对」标记
本地独有 若该记录在云端账本代次内不存在，视为本地新增 → 上传
云端独有 视为其它设备新增/修改 → 拉取覆盖本地
```

旧设计里「保留本地版本并让用户逐条核对」的路径废弃。

## 二、数据修复（手动入口，严格照一木）

入口位置：我的 → 云同步（子页），对应 `fragment_my.xml` 的云同步入口。

弹窗一：重新云同步（对应 `dialog_data_sync_all.xml`）

```
标题   重新云同步
说明   必须仔细阅读：
       此操作会清除云备份并重新上传本地数据，如果当前本地没有数据或数据有误，千万不要执行此操作
正文   本地账单数量：{n}
       云备份账单数量：{m}
按钮   取消 / 确认
动作   DELETE 云端账本数据 → 将本地全量上传为新的云端基线
```

弹窗二：重新下载备份（对应 `dialog_data_sync_download.xml`）

```
标题   重新下载备份
说明   此操作会重新同步云备份数据至本地，如果当前云备份数据有误，建议不要执行此操作
正文   本地账单数量：{n}
       云备份账单数量：{m}
按钮   取消 / 确认
动作   用云端全量覆盖本地（本地多余记录被丢弃）
```

## 三、数量来源

```
本地账单数量   本地 state.bills 中属于当前账本、未删除的条数
云备份账单数量 服务端 book 下 kind=bill 且未删除的条数
               需要新增接口：GET /api/data/counts?bookId= 或在 pull 响应里带 counts
```

## 四、与旧设计的差异（要删的代码）

```
删除  按 reason 文本匹配清理冲突（discardBaselessConflicts 的文本判断）
删除  「冲突保留本地 + 查看两份内容 + 使用云端版本/保留本地版本」逐条核对 UI
删除  App 顶部「有 N 条记录待核对」长期提示
保留  recordKey / version / generation / operationId 这套协议（服务端仍需要）
保留  pending 队列（离线补传），但补传失败不再标记为长期冲突
```

## 五、验收标准

```
1 我的 → 云同步 子页：显示「本地账单 N 条 / 云备份 M 条」与两个修复按钮
2 点「重新云同步」：二次确认 → 云端清空并上传本地 → 数量变为 N = M = N
3 点「重新下载备份」：二次确认 → 本地变 M 条
4 日常记账不再产生「待核对」长期提示
5 npm run check 全绿；生产/staging 走查 11/11；写操作 4/4
```

## 六、CR 要求

```
模型   deepseek-v4-pro
重点   是否与一木一致（上述两个弹窗的文案、数量、动作方向）；
       是否存在「清云端」不可逆操作缺少二次确认；
       计数口径是否与服务端一致
```
