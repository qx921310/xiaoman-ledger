## P1 迁移冲突中的隐藏草稿可能被用户无意删除

`src/features/book-pending.ts:138-161` 发现 scoped / global 两个旧草稿不同时，只将 scoped 草稿存到 IndexedDB，global 仍留在旧键。账本管理页面的冲突操作只有「保留本地」「用云端」，没有展示 global 与 scoped 的内容供对比，也没有让用户选择某个旧草稿。`src/features/book-pending.ts:576-586`、`:608-610` 在用户点「保留本地」后直接删除两个旧键。

隔离复现：scoped 的账本名是 `scoped draft`，global 的账本名是 `global draft`；迁移后点击保留本地，只有 scoped 被提交，两个旧键均被删除，global 草稿消失。测试虽然称“用户取舍后才清理”，但并未让用户看到或选择另一份旧草稿。

建议将所有候选及其来源保存为可恢复记录，界面显示具体差异及各候选、支持导出或分别选择；仅在明确选择且完成安全保存后处置其他候选。解析失败的原始 global 旧键也不能在处理 scoped 时因空 `remaining` 被删除（`:212-221`）。

## P1 编辑可把可写账单转移到只读账本

`src/store.ts:1278-1291` 的 `updateBill` 检查旧账单的账本，却允许 `Partial<Bill>` 中的 `bookId` 覆盖目标账本。隔离复现：将所属账本 1 设为 peer、账本 2 设为 silent，调用 `updateBill(id, {bookId: 2})` 返回 true，账单归属变为 2。此为命令层复现，未声称当前编辑页面暴露账本选择。

建议禁止通用编辑修改身份及账本归属；如确需移动账单，单独设计命令，校验源与目标权限及退款、报销、组等关联，定义迁移原子性与服务端校验。

## P1 AA 分账只校验当前账本，没有校验关联群组

`src/store.ts:594-600` 的 `addSplitExpense` 检查 `currentBookId`，却按传入群组 ID 选成员，既不校验群组归属和权限，也不校验群组、成员和新增费用属于同一账本。隔离复现：当前账本 1 可写，AA 群组和成员属于只读账本 2，仍返回 true，生成 `bookId=1`、`splitGroupId=只读账本群组` 的跨账本关联。`setBillSplit` 也应以同一原则核对参与群组和账单。

建议以目标群组的实际账本作为权限与归属来源，逐一确认群组、成员、账单的存在、归属和写权限，拒绝跨账本，测试不同当前账本及历史缺失归属。

## P2 新增只读异常未接入部分页面的失败提示

`src/store.ts` 的 `addSplitGroup`、`addSplitMember`、`addStockAsset` 等现在会在只读时抛错，但 `src/features/split.tsx:43-44`、`src/features/settings.tsx:1207`、`src/features/assets.tsx:389` 没有捕获。当前账本只读时操作会抛出未处理异常，而非按预期给出提示。建议命令统一返回结构化结果或在所有调用点捕获，保留表单并提示用户。
