## 二、本轮新增的多设备验证（关键证据）

方法：两个独立子代理扮演两台设备，同一账号（dual2@xiaoman.test）、同一个账本（bmwhhfw6t）并发写入；
裁判脚本只看云端结果与两端日志，不看界面。

```
设备 A  6 笔新建（1..6 元）+ 1 条幂等探针（9 元，同一 operationId 连发两次）
设备 B  同上，与 A 并发、抖动 120–500ms，且故意用 baseVersion=999 冲撞一次
```

云端裁判（scripts/dual-verify.mjs）：

第一轮（固定前缀统计，已被 Codex 指出可能假 PASS）：
```
total 14 / deviceA 7 条 30 元 / deviceB 7 条 30 元 / duplicateIds 0 → PASS
```

第二轮（精确集合核对，runId=run-1115-precise，取代上面的统计口径）：
```
node scripts/dual-verify.mjs --run run-1115-precise
{ "expected": 14, "cloudRunPrefixed": 14, "missing": [], "duplicated": [], "unexpected": [], "verdict": "PASS" }
```
判定依据：两台设备日志里的 expectedIds（各 6 条 create + 1 条幂等探针）逐条必须在云端存在且唯一，
且云端不得出现本轮 runId 之外的记录 —— 不再依赖「数量不少于预期」。

接口说明：`--run` 必填且两端一致；`dual-verify` 只用 `--run`，
不再接受 `--tag-prefix / --expect-each` 这类按数量判断的旧参数。

关键结论：

```
· 并发写入不丢、不重、不串：14 = 6×2 + 2 条幂等探针
· 幂等真正生效：同一 operationId 发两次，云端只落 1 条（duplicates=0）
  但两次回执 status 都是 accepted，而非显式的 duplicate 语义 —— 建议服务端明确回执状态
· 陈旧 baseVersion 被拒：version-conflict，且被冲撞的金额未变（仍为 2 元，不是 777）
```

复现命令：

```
# 两台设备必须使用同一个 runId；裁判也用同一个 runId 做精确集合核对
node scripts/dev-sim.mjs --device A --email dual2@xiaoman.test --password DualTest12345 --count 6 --tag sim --run run-1115-precise
node scripts/dev-sim.mjs --device B --email dual2@xiaoman.test --password DualTest12345 --count 6 --tag sim --run run-1115-precise
node scripts/dual-verify.mjs --run run-1115-precise
```

## 三、服务端权限独立验证（绕过前端）

```
非成员 push 账单            → results[].status = permission-denied，denied=1
非成员改账本名              → BOOK_FORBIDDEN「只有「管理」可以修改账本」
silent 成员 push（插库构造）→ permission-denied
改成 peer 后同一请求        → accepted, version=1（正向对照）
```

结论：`roleOf + canWrite` 在服务端真实生效，不是只在前端拦截。
副作用发现：共享账本的 invite/join/role 接口在代码里整段注释停用（产品决定），
因此 silent 角色只能通过历史数据或插库出现 —— 这是产品决策，不是缺陷。
