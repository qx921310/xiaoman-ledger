# 多设备同步协议 v2：实施约束与验收

状态：设计中，尚未启用。基线 `e9155e5`。目标：修复 CR-2 不同时间戳并发覆盖、CR-4 清空前未上传的离线新增；会话取消另行实施。此文不是已完成声明。

## 核心约束

1. 每条记录以既有作用域 + kind + 稳定 ID 标识，服务端持久化单调递增 revision；每个账本维护 generation，清空原子递增。
2. 设备必须在第一次本地修改发生前保留自己实际观察到的 base revision 与 generation，随草稿一起持久化。不能在重连后先拉最新版本再替离线草稿换上最新 base；那会把真实冲突伪装成安全更新。无法证明历史草稿基线时标记待核对，不猜。
3. 推送前不得把未变更记录当修改。仅推送待确认的本地变更，以稳定 operationId 幂等重试；本地新改动不能被在途请求的回执覆盖。服务端以客户端 base revision 作 compare-and-swap，绝不依赖客户端时间来决定冲突胜负。
4. 记录创建、修改、删除和关联引用写入要有一致的原子边界；包括账单与退款、转账与手续费账单、周期期号。服务端拒绝某个操作不能被客户端当作同步成功。
5. 服务器在单一事务内比较账本 generation、写入相关墓碑、递增 generation、更新期号；旧代次操作无论是否已在服务端出现都不得生效。离线草稿保留，标明清空后待核对；用户可导出或显式选择以新操作重新添加，不可静默丢弃或自动复活。
6. 并发冲突应同时保留服务端版本与本地修改内容，包含删除/修改冲突、账单与退款关联；未经用户确认不得自动覆盖。保留状态在重启后仍然存在，能查看、导出和按用户选择产生带新 base 的解决操作；旧版 time LWW 合并不可覆盖草稿。
7. 用户切换时撤销在途请求、隔离响应和调度状态；中止 HTTP 不保证服务器未收到或未执行请求，操作 ID 重试须幂等。持久化命名按账号隔离；任何旧响应不能写入新账号存储。

## 协议草案

- `pull` 返回授权范围内的记录及 revision、账本 generation、墓碑、服务端游标。全量快照初期可用，但不能据此覆盖本地脏数据；游标和增量优化不是首版前提。
- `push` 带协议版本、operationId、scope、kind、id、observedGeneration、baseRevision、变更内容或删除意图；返回每条 `accepted`（revision）、`already-applied`、`conflict`（当前服务器版本）、`stale-generation`、`denied` 等可恢复结果。
- push 结果与拉取结果须与发送时的具体草稿指纹对应；如果用户在请求途中再次修改，不得清除后续变更标记。先写本地持久队列再发送；服务器提交后响应丢失，重发同 operationId 得到相同结果。
- 已存在记录首次升级无法证明 base 时，先比较本地与服务端业务内容；一致可建立基线，不一致保留为待核对。generation 不明且账本发生过清空时，未上传记录一律待核对，不按时间或记录是否存在猜测。
- 迁移时数据库备份、建表/加列、回填、版本门槛和回退演练须原子/可恢复。旧客户端若仍能用旧 `/data/push` 写入会绕过所有保护；发布必须有明确服务端兼容策略：旧客户端禁止写入并提示升级，保留其本地未同步数据且提供安全迁移／导出路径；不得默默回退旧协议。
- 现有版本无持久化可靠 outbox、冲突处理页和幂等操作表；仅加两列不等于完成本协议。尤其不能把一整个旧 JSON 快照无差别自动迁移成新代次的所有新操作。

## 最低验收

- 相同基线 A/B 分别以不同时间编辑同一账单，任意顺序推送：一方 accepted，另一方冲突，两份版本跨重启可恢复。
- A 清空，B 持旧代次且有服务端从未见过的离线新账单：服务端不落地，B 草稿可见；确认恢复后以新代次和新 operationId 写入一次。
- 清空和离线退款、转账、手续费、周期在不同顺序和部分失败下不丢失/重算错误；编辑与删除冲突同理。
- 服务器执行成功但响应丢失；同 operationId 重试不重复、事务只发生一次；用户在请求中继续编辑时不丢后续修改。
- 旧客户端写请求被阻止且本地数据不丢；历史本地与云端相同、不同、缺标识、已清空分别迁移；回退和旧数据库完整性验证。
- 两个独立浏览器存储、同账号离线/重连、双设备先后推送、账号切换延迟请求、余额及重启；真实 iPhone 额外测试休眠与恢复。
