# 小满记账验收结果（2026-11-11）

## 结论与边界

**本轮不通过，尚不能将清单中的模块全部标记为验收完成。** 主要阻塞是数据不能随同步或“完整备份”迁移、周期冲突可能误删、多人账本私有账户信息泄露、AA 和投资计算有明确错误。

- 被验收代码：`720b79eb9724336cee6069b864e17ecece8b7b6a`，检查开始时工作区干净；收尾时其他协作者正在修改 `src/App.tsx` 和 `src/features/add-bill.tsx`，这些未提交改动不在本次结论内。原清单：`docs/验收清单-2026-11-11.md`。
- 执行：`npm run check` 七项通过，包括 typecheck、现有测试、图标、视觉令牌、对比度、lint、构建；Vite 有一个既动态又静态导入的分包提示。通过不代表业务验收通过。
- 测试：用隔离 Node 状态、虚拟账号和复制到临时目录的独立 SQLite 服务端；无真实账本写操作。截图识别未向第三方发送用户图片；行情只使用公开代码进行只读查询。
- 下文区分“隔离复现”“静态检查”“未测”。实测不等于真实 iOS、多设备、生产环境全链路验证；不能据此宣称 23 个模块全部验收。

## 必须修复的发现与参考方案

### P0-1 新功能没有跨设备同步或完整备份，存在数据丢失风险

- 位置：`src/sync.ts:17-29,40`；`src/store.ts:1202-1223,1447-1472`；`src/backup.ts`。
- 隔离复现：创建一个 AA 群组和一个投资持仓后，`collectRecords()` 不包含二者，`exportAll()` 也没有 `splitGroups` 或 `stockAssets`。同类缺项还包括 AA 成员/分摊、投资交易、模板、房贷、分期、账单组及关联。它们在本设备 Zustand 本地存储中，不会因此自动出现在另一设备/JSON 导出。账单中的 AA 引用却可能独立同步，形成悬空引用。
- 建议：先明确每类数据是个人作用域还是账本作用域及权限；统一纳入同步、作用域匹配、版本、墓碑、导入导出与恢复，建立有版本的备份格式和旧备份迁移。现阶段界面不能称之为“完整备份”。
- 回归：A 创建每类记录→同步→B 拉取；删除→另一端删除；JSON 导出→空环境导入→核对所有实体与关联；断网/切账号/旧版备份迁移。

### P0-2 周期冲突仍可能删除不同内容或关联退款的账单

- 位置：`src/store.ts:1231-1257`、`src/sync.ts:88-101`。
- 隔离复现 1：两条候选金额/时间/分类/备注相同，但 `assetId` 和 `tags` 不同，结果 `{dropped:1, kept:0}`，本地候选被删。余额所属账户或用户标签的差异不能忽略。
- 隔离复现 2：历史/导入等 `billId` 与 `syncId` 不同的状态下，退款按 `billId` 关联，而 `linked` 只拿 `syncId` 查；本地账单被删后退款仍指向旧 `billId`。新周期账单通常两 ID 一致，但兼容路径不能假设永远一致。
- 建议：复用并完善 `cycle-dedupe.ts` 的业务内容比较，覆盖账户、币种/金额快照、标记、标签、附件等；所有关联按明确的稳定身份和实际 billId 找，覆盖退款、报销、转账/AA/账单组等。胜出数据缺失、存在任一疑点时保留并提示；回执及墓碑操作要幂等。
- 回归：不同账户/标签/币种/附件、引用、历史双 ID、拉取失败、重复回执、两设备同周期及余额一致性。

### P1-1 单人账本变多人后会泄露历史私有账户名称

- 位置：`src/features/add-bill.tsx:108-114`；`src/domain/asset-scope.ts`；`server/server.mjs:480-568`。
- 隔离服务复现：A 把带“虚拟私有账户”名称快照的账单写入单人账本，邀请 B 加入；B 调用 pull 返回该历史账单及账户名。新增时按成员数拦截无法覆盖以后邀请成员；其他写入路径或直接 API 也绕过前端判断。
- 建议：先定义共享账本里私有账户的展示策略：服务端校验所有写路径、对不应共享的账户快照脱敏，或在邀请/共享前明确提示并处理既有历史；不能只藏前端。成员加入、退出及缓存同步都要执行相同规则。
- 回归：先单人记账后邀请；两人同时记账；OCR/导入/模板/编辑/周期/转账路径；旧成员重拉、退出后拉取及附件。

### P1-2 AA 按金额允许误差 0.01 元并悄悄改变输入

- 位置：`src/domain/split.ts:53-70`、`src/store.ts:429-431`。
- 隔离复现：账单 10 元，输入 5 和 5.01 元被接受，输出变为 5+5。`0.011` 容差大于一分钱，违背清单的精确校验。
- 建议：金额先转换为整数分，所有输入必须是有限、非负、精确到分；按金额的分值总和必须严格相等，不得静默重写；份额与均分尾差规则另行明确。
- 回归：相差 ±0.01、0.001、负数、空输入、0.1+0.2、三人尾差及大数。

### P1-3 不同 UUID 账单的 AA 支出互相覆盖

- 位置：`src/store.ts:424-445`、`src/features/bills.tsx:408`。
- 隔离复现：两条字符串账单分别应用 AA，`sourceBillId: Number(bill.billId) || 0` 都变成 0，第二次按 sourceBillId 过滤并覆盖第一条；结果只有一条 splitExpense。
- 建议：类型和关联键使用完整稳定字符串/原始 `string | number`，统一比较函数；迁移已存的 0 无法自动确定归属时标待核对，不猜。与 P0-1 一起补跨端同步和备份。
- 回归：两条 UUID 分摊、编辑其中一条、删除/恢复、重登、同步及备份恢复，验证两条明细仍独立。

### P1-4 后进先出重复卖出成本顺序错误

- 位置：`src/domain/stock.ts:83-99`。
- 隔离复现：批次各 1 份、成本依次 10/20/30；每次卖 1 份、收入 40，LIFO 第一次利润 10，第二次应该再获利 20，累计 30；实际累计 40，因为第一次返回批次顺序倒置，第二次扣了成本 10。
- 建议：按下标逆序遍历但保持批次数组始终按创建顺序；用整数或十进制定点约定结转精度，明确手续费。
- 回归：三批次连续部分卖出、跨批次、清仓、FIFO/LIFO 交替以及手续费。

### P1-5 期初持仓缺批次，成本法切换不回放

- 位置：`src/store.ts:455-470,480-516`；`src/domain/stock.ts:76-106`。
- 隔离复现：期初持仓 10 份、成本 10；设 FIFO，再买 1 份成本 30；卖 2 份返回 false，因为 lots 只有后来买的 1 份。加权法卖出后又会丢批次。`setStockCostMethod` 只改方法标记，没有重算历史交易，无法支持清单宣称的“切换三种成本法后盈亏随之变化”。
- 建议：定义期初批次、交易不可变顺序及切换口径；以期初状态 + 全部买卖交易按选定方法重放计算，保证持仓份额、批次和成本一致；不能可靠重建时明确提示，禁止静默用平均成本冒充 FIFO/LIFO。
- 回归：期初建仓→多次买卖→切法→核对每期成本和已实现收益→重登/同步→再交易。

### P1-6 分期用金额和日期去重，会漏掉第二个独立计划

- 位置：`src/store.ts:581-602`。
- 隔离复现：同账户创建两个各 120 元、2 期、同月同费率但彼此独立的分期计划；第一个生成 2 条，第二个生成 0 条。仅凭账户+时间+金额判重会把真实账单当重复。
- 建议：每期使用稳定业务身份 `(账本, 分期计划 ID, 期号)`，依此幂等；在记录中持久化关联，并使用服务端唯一约束处理多设备；不要以金额相同视为同一笔。
- 回归：两个同金额独立计划、重复点击同计划、跨设备离线生成、删除/恢复。

### P1-7 OCR 识别结果无法修正，可能写错账户或方向

- 位置：`src/features/settings.tsx:376-396`；`server/server.mjs:600-649`。
- 静态检查：确认区域只展示不可编辑字段，直接选 `assets[0]`，分类按名称找（未限制 kind），金额和日期未做可靠有效性检查；支付方式仅展示/未用于确定账户。识别不准时无法在保存前修正，也可能绕过私有账户检查。
- 建议：预览改为可编辑表单，明确收入/支出、日期、金额、分类与账户，用户确认后调用统一记账命令与权限/汇率校验；失败保留草稿。服务端限制图片大小、格式和访问频率，并明确外部识别服务处理图片的隐私范围。
- 回归：识别错方向/账户/日期/金额、0 和非数、收入同名分类、共享账本私有账户及外部服务不可用。真实截图测试需用户同意发送到指定识别服务，先使用人工构造测试图片。

### P1-8 共享账本附件对其他成员不可见

- 位置：`src/features/bills.tsx:620`、`server/server.mjs:653-685`。
- 隔离服务复现：A 上传附件只带 name，B 非成员请求 403；B 加入相同账本仍 403。服务端只有在上传时收到 bookId 才记录共享归属；当前客户端没有传。独立私有附件的 403 是正确的，不应放宽到所有登录用户。
- 建议：上传绑定账本和账单稳定身份，服务端先校验写权限再落盘、验证关联，下载每次校验当前成员权限；处理旧附件归属迁移、失效成员及缓存时效。
- 回归：A 上传后同账本 B 可看、非成员 403、移除成员后 403、静默成员写入被拒、换账号后缓存不能越权。

### P2-1 行情接口返回中文名称乱码

- 位置：`server/server.mjs:577-594`。
- 隔离服务对 `sh600519` 请求返回有效正数价格，但中文名称为乱码；当前以 `r.text()` 默认 UTF-8 解析，行情源文本编码须按实际响应确认。
- 建议：用受控的编码解码与超时/上游状态校验，校验股票、基金等代码格式和错误数据；界面保存价格并展示来源/时间。回归用可重复的编码样本加线上只读联测。

### P2-2 财务交易生成账单的方向/分类值得阻断

- 位置：`src/store.ts:490-499,581-602`。
- 静态检查：投资交易 `addBill` 对买入和卖出均用相同分类 `parentCategoryId:4` 及同一账户，不区分资金流向；分期按本金+手续费生成支出，若原消费已记账会重复计支出。需先确认产品希望“交易是资产转移还是收支”的会计口径，不能贸然修补。
- 建议：建立交易与账户资金事件关联、明确费用/本金如何计入统计及原始消费去重；默认关闭有歧义的自动记账并明确提示，完成数据迁移与对账后开放。
- 回归：买入→卖出→账户、资产市值、已实现/浮动盈亏与收支；已记消费→分期→还款不能重复计支出。

## 建议修复顺序

1. P0-1、P0-2、P1-1：先建立备份与同步保障、停止可能误删/泄露的行为，涉及真实数据的迁移先只读扫描并备份。
2. P1-3、P1-2、P1-4、P1-5、P1-6：修正 AA、持仓、分期的身份与金额计算；每条先建失败用例，再修复并验收。

4. 固定新提交后重跑七项检查、全部回归和隔离服务验证；再用专门的测试账号及虚拟数据进行双设备真机验收。线上部署版本、真实 OCR 服务及用户历史数据不在本轮结论中。
