## P0 问题（需优先修复）

### 1. P0-2 同步成功会再次触发同步，形成自循环

**复现：**用实际 store、dirty bus 和调度器，在模拟同步中调用真实的 `setSessionSyncAt`，无任何用户输入，200 毫秒内触发 5 次同步（主动停止于第 5 次）。

**原因：**`src/store.ts:185-205` 的封装 `set` 对任意状态更改均 `markDirty()`；`src/sync.ts:121-123` 在 `endRemote()` 之后调用 `mergeTaxonomy`、`dedupeCycleBills`、`setSessionSyncAt`、`setLastSync`，即便同步产生的状态也会变脏。`src/sync-auto.ts:63` 完成后 pending 会零延时再跑。

**影响：**空闲时连续读写请求、反复全量推拉、耗电和服务器负载；频繁同步放大其他冲突。现有调度测试只用独立 mock 函数，未连接真实 store + `syncNow`。

**建议：**按业务实体实际变更打脏标记，会话/最后同步时间/UI 状态不触发；同期冲突消解、分类变更等仅在确有需要上传的变更时入队。将远端应用与同步元数据排除出本地脏事件，且避免“无实际变化”的 set 触发。回归：真实 store + 模拟服务完成一次同步后，跨多个防抖时间无新请求；同步中本地修改仍须补跑一次；失败重试不产生忙循环。

### 2. P0-3 相同记录重推被误报冲突，客户端丢弃冲突回执

**复现：**向隔离服务以相同 ID、相同时间和完全相同 payload 重推一条账户记录，结果 `accepted=0, conflicts=1`，本应幂等成功或跳过。两设备同时间写不同内容时，服务器保留第一版，但第二方没有收到应用层可处理的冲突提示。

**原因：**`server/server.mjs:553` 的 SELECT 未读取 `payload`；`:590` 却比较 `mine.payload`，因此它总是 `undefined`，所有正常同时间非空 payload 都被判为不同。即便 SELECT 修正，服务端会为账单附加 `ownerId/memberNo/sequenceNo/displayId`，重推还需明确比较规范化的业务内容，不能直接比较原始 JSON 字符串或字段顺序。`src/sync.ts:103-130` 只读取 `authoritative`，忽略 `conflicts/conflicted`；调度器只要 Promise 不抛错就报告成功。

**影响：**大量重推被错误标为冲突；真正不同内容未有可见告警、没有服务端冲突副本；后续拉取/重启可能丢本地版本。不同时间戳的并发修改仍直接按客户端时间 LWW 覆盖，不只“同毫秒”需要保护。

**建议：**选择并实现统一版本协议（服务端版本/基版本、显式冲突），先用实际读取的业务字段规范化比较；同一版本不同内容持久化双方可恢复内容并返回可操作回执，客户端保存并显示，不更新成功状态。不要以客户端时间先后代替并发判定。回归包括：完全相同推送、账单服务端附加字段重推、JSON 键顺序、相同与不同时间戳并发修改、删除与修改冲突、第二设备重启、对端已完成推送但拉取失败。

### 3. P0-1 新实体删除未写墓碑，重同步会复活

**复现：**真实 `useLedger` 新增并删除模板后调用实际 `collectRecords()`，没有该模板的删除记录。源码同类路径包括 `deleteSplitGroup`/`deleteSplitMember`、`deleteStockAsset`、`deleteTemplate`、`deleteHomeLoan` 等，只从数组过滤。

**影响：**A 删除后，服务端没有被告知；下一次拉取旧记录会恢复，B 也不会删除。群组删除还牵涉成员/支出，投资删除牵涉交易记录，可能出现悬空引用。现有 `tests/sync-multidevice.test.mjs` 直接手工构造 tombstone，没有调用真实删除动作，不能证明端到端。

**建议：**逐实体建立删除契约和同事务墓碑，覆盖级联／阻止删除策略；对依赖对象带正确作用域和稳定 ID。通过真实 store 创建 → collect → 服务端 → 另一 store 拉取 → 删除 → collect → 重启反复同步验证，不要只手写假数据。

### 4. P0-5 清空防复活只覆盖服务端已存在记录，未覆盖离线未上传与错误时间

**复现 A：**清空账本后，以清空前旧时间首次上传一条此前仅存在离线设备的新账单；`accepted=1`，该账单仍为有效记录。**复现 B：**创建真实转账后其 payload 不含 `bookId`，清空按 `book_id` 扫描时没有处理，隔离服务测试同样保留了无作用域转账。

**原因：**`server/server.mjs:517-521` 只把已保存且属于该账本的记录标记墓碑，无账本代次屏障；从未上传的离线记录在云端没有墓碑。`src/store.ts:752-765` 创建 `Transfer` 没有填写账本归属。清空墓碑时间使用服务端 now；离线设备时钟超前的新版本仍可超过墓碑。清空还独立删除 `bill_periods`，恢复和中断一致性需验证。

**建议：**账本清空代次/服务器版本在客户端持久化并随写入发送；旧代次记录不静默删除，转为可核对或导出冲突；在事务中更新代次、墓碑与期号策略。所有相关实体赋予正确账本作用域，历史无法确定的不猜。确认产品是否要保留清空前离线新增作为待恢复草稿，不能用机器时间判断用户意图。回归：已上传旧记录、未上传离线新纪录、后续修改、未来时钟、重复清空、退款/转账/周期和跨设备重启。

## P1 问题及验证范围

### 5. P0-4 转账 ID 已改为 UUID，但账本归属仍不完整

`src/store.ts:722-725` 创建转账使用 UUID，保留旧数值 ID，编辑沿用原 ID；100 并发测试通过，**这一项 ID 撞车修复可以认可**。但实际 store 新转账未设置 bookId，手续费墓碑有无 bookId 还取决于是否有手续费账单，导致其按个人范围同步；见第 4 条。当前并发测试手动构造新转账，不等于真实前端操作链路与余额验收。建议补真实 store → collect → 服务端 → 另一设备 → 编辑/删除/清空的双账本对账。

### 6. 账号切换／手动同步未纳入同一串行队列

`src/App.tsx:32-33` 启动自动调度后又直接 `syncNow()`；`src/features/settings.tsx:142` 也直接 `syncNow()`，绕开 `sync-auto.ts` 的 `inFlight`。`src/App.tsx:logout` 未调用 `startAutoSync` 返回的清理函数，且 `stopAutoSync()` 本身也不移除监听；用户退出／切换账号时已发请求可能晚返回并落到新账号状态。此条为静态风险，尚未完成延迟响应复现。

**建议：**所有入口走同一生命周期受控的队列；区分账号会话代次，退出取消计时与订阅、隔离或中止在途请求，旧结果不可应用到新账号。测试：首次同步未完成时本地写入、连续点击手动同步、退出后另一账号登录再释放旧请求、登出后的前台/网络事件。

### 7. WAL 启用，但现有在线复制数据库的备份脚本不安全

`server/server.mjs:15-17` 已配置 `journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`。但 `deploy/reset-data.sh` **在停止服务前只复制 `ledger.db`**；WAL 模式下已提交数据可能仍位于 `ledger.db-wal`，所得备份可能缺少最近提交。此为 SQLite WAL 机制与脚本静态分析，未对生产数据做试验。`NORMAL` 在断电等情况下也不应笼统称“所有已提交事务绝不丢失”。

**建议：**改用 SQLite 在线备份 API/`.backup`、或停服务并完成正确 checkpoint 后备份一致快照；对恢复副本做完整性检查和关键记录对账。部署、重启、checkpoint、磁盘占满、恢复与性能在隔离环境单独测，不能仅凭基准耗时认定 WAL 正确或更快。

### 8. 同步失败、拒绝、冲突均可能显示成功

`src/sync-auto.ts:48-50` 忽略 `syncFn` 的业务返回值；`src/sync.ts:127-130` 返回 denied 等但未返回服务端 conflicts，`src/App.tsx:226-230` 使用 lastOkAt 展示“已与服务端一致”。发生服务端拒绝或冲突时 Promise 仍然 resolve，也可能显示已同步。建议同步结果显式分类：成功、部分拒绝、冲突、失败；保留未确认记录并提供处理入口，只有全部确认后才能展示一致。
