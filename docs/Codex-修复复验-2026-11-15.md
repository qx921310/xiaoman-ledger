# 修复复验：2026-11-15

复核版本：`5e8fbaf`，对比 `5cf1786`。结论：**暂不建议上线生产**。本次使用本地隔离数据和故障注入，未操作生产或 staging 数据。`npm run check` 通过；这不覆盖下列组合场景。

## P1-1 跨币种账户的账单仍可拆分，改变余额

`src/store.ts:1028` 仅判断 `origin.currencyInfo`。人民币计价、从美元账户支付的账单可以没有该字段，但仍有以美元冻结的 `accountAmount`。隔离复现：USD 账户期初 1000，汇率 7.2 时支出 720 CNY，余额 900 USD；汇率改为 8 后拆为 360 + 360，返回成功，账户余额变为 905 USD（两笔分别扣 50、45 USD）。

建议暂时拒绝所有涉及跨币种核算的拆分，依据原账单 `accountCurrency`、账户币种和本位币等实际币种关系判断，而非仅依赖展示字段；同时校验分录目标账户。覆盖历史记录缺字段、跨账户和汇率变化的测试。若未来支持，应冻结并分摊原账单账户金额，明确跨账户口径。

## P1-2 中途失败的拆分回滚会留下错误余额

`src/store.ts:237` 的 `rollbackBills` 使用 `useLedger.setState`，绕过受控 `set` 的余额重算。故障注入：100 元期初、30 元原支出，拆为三笔；第二个新建操作抛错后返回 false，账单恢复为一笔，但余额从 70 变为 60。正常业务中需要发生中途异常才触发；测试证实失败路径不满足回滚承诺。当前“拆分回滚不留同步墓碑”测试并未制造失败。

建议将拆分及成组预先计算并一次受控提交，失败无状态变更；如果仍使用回滚，必须重算所有派生值并处理可能已经入队/发送的中间状态。测试须注入每一步失败并核对账单、余额、墓碑和同步队列。

## P1-3 队列并发编辑仍会丢失原发送快照

`src/features/book-pending.ts:165-173` 新建记录时没有保留 `existing.sending`；此外 `:320-326` 网络错误时无条件清掉它。A 已发送、期间入队 B、服务端接收 A 但响应丢失时，下一次只能携带 B 的新 operationId 和旧版本发送，可能产生假冲突，无法按这次新增的 `:260` 原样重放 A。现有测试分别覆盖响应丢失和在途编辑，但未同时覆盖。

建议独立持久化不可变 in-flight 快照与后续草稿；网络异常保留快照及原 operationId，收到幂等回执后推进版本再发送 B。增加 A 在途时 B 入队、A 成功但响应丢失、应用关闭重开、随后自动重试的组合测试。60 秒租约到期后也需要可靠定时唤醒：目前 `src/App.tsx:67-89` 主要依赖登录、上线、回到前台事件，停留前台并不必然再次触发。

## P1-4 只读守卫仍不完整

`src/store.ts:1181` 的 `updateBill`、`:1381` 的 `addReimbursement`、`:959` 的 `createBillGroup` 均未检查目标账本权限。隔离测试将已有账单账本设为 `silent`，直接调用 `updateBill` 仍能把金额改成 100；退款的新增守卫可以拒绝同场景。`updateRefund`、`deleteRefund`、组合修改/解散、报销结算等也应按目标实体和所属账本检查。

建议统一盘点所有记账业务写命令，按目标实体所属账本在命令层拒绝只读，并返回可展示的失败原因；涉及多实体时逐个验证。账本缺失的历史记录不要默认推断有写权限，应定义迁移/核对策略。服务端对共享账本的实际角色也须独立鉴权，不能仅依赖本地 role。若产品正式取消只读角色，则先明确迁移与服务器兼容策略。

## P2 退款日期与换算显示仍不一致

`src/domain/asset-trend.ts:76` 已采用业务日期，但 `src/domain/account-history.ts:72` 仍使用更新时间；同一退款在走势和账户流水里日期可能不同。`src/features/bills.tsx:813-814` 的折合金额仍按原支付账户 `a.currency`，而不是选中的退款账户，切换账户币种后可能误导用户。分别使用退款业务日期与所选账户币种，补跨日期、跨币种用例。
