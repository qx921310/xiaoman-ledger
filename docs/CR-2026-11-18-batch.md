- 结论：不通过（存在删除外币报销时资产扣减未按汇率折算的余额错误，以及多处命令层缺少只读账本权限校验，可能绕过历史只读账本）

- 问题列表：

1. **P0** 位置：`src/store.ts` `deleteReimbursement` 方法内  
   现象：删除已结算（`status==='done'`）的报销时，资产扣减使用 `current.number`（本位币金额），未按汇率折算为账户币种，与结算时入账金额（`rec.number / rate`）不一致。  
   复现要点：创建外币账户（如 USD，汇率 7.2），登记一笔 100 元报销并结算，账户余额增加约 13.89 美元；随后删除该报销，账户余额减少 100 美元，余额错乱。  
   修复建议：资产扣减应使用 `current.accountAmount` 或 `current.number / rate`，与 `settleReimbursement` 中的入账逻辑保持一致。

2. **P1** 位置：`src/store.ts` 多个方法：`addAiTypeRule`、`updateAiTypeRule`、`deleteAiTypeRule`、`addDream`、`updateDream`、`deleteDream`、`deleteStockAsset`、`setStockHidden`、`setStockPrice`、`setStockCostMethod`、`addTemplate`、`deleteTemplate`、`addHomeLoan`、`deleteHomeLoan`、`addInstalment`、`deleteInstalment`  
   现象：这些方法直接操作账本相关的实体（AI 规则、愿望、持仓、模板、房贷、分期），未调用 `bookWritable` 校验所属账本或当前账本的可写权限。  
   复现要点：在 UI 或控制台调用这些方法（例如通过 `useLedger.getState().deleteStockAsset(id)`），即使目标实体属于只读账本，仍可成功删除/修改/新建，绕过历史只读账本限制。  
   修复建议：为所有涉及账本归属的写操作添加 `bookWritable` 检查，以实体现有 `bookId`（或目标 `bookId`）作为校验依据。

3. **P1** 位置：`src/store.ts` `runCycles` 方法  
   现象：周期账单生成时未检查周期规则所属账本是否可写，直接通过 `set` 将生成的账单插入 `bills` 数组，并调整资产。若周期规则属于只读账本，该账本仍会被写入账单。  
   复现要点：创建或拥有一个只读账本的周期规则，调用 `runCycles`（正常自动运行或手动触发），在只读账本下生成账单并修改余额。  
   修复建议：在 `runCycles` 中对计划中的周期规则逐条检查 `bookWritable(cycle.bookId)`，任一不可写则跳过或整体拒绝。

4. **P1** 位置：`src/store.ts` `postInstalmentBills` 方法  
   现象：生成分期账单时未使用分期计划记录 `rec.bookId`，而是通过 `get().addBill()` 使用 `currentBookId` 作为账单账本，导致分期账单被记入错误的账本；同时未检查分期计划所属账本是否只读，可能绕过只读限制。  
   复现要点：在只读账本中创建分期计划（若 UI/API 允许），切换当前账本为可写账本，执行 `postInstalmentBills`，生成的账单被记到可写账本而非分期计划账本，且只读账本不受保护。  
   修复建议：在 `addBill` 时显式传入 `bookId: rec.bookId`，并在方法入口检查 `bookWritable(rec.bookId)`。

5. **P2** 位置：`src/store.ts` `deleteAsset` 方法  
   现象：删除账户时未检查该账户是否被账单、转账、借贷、流水、报销或退款等记录引用，可能导致悬挂引用，后续统计或编辑相关记录时出现异常。  
   复现要点：删除一个存在多笔账单的账户，之后查看历史账单或执行涉及该账户的操作（如编辑、删除关联账单）可能报错或显示异常。  
   修复建议：在删除前检查所有相关业务表，若存在引用则拒绝删除并提示用户，或提供级联处理。

6. **P2** 位置：`src/store.ts` `updateTransfer` 方法  
   现象：更新转账时先撤销旧转账（删除 transfer、删除手续费账单、冲正资产），然后调用 `addTransfer` 创建新转账。若 `addTransfer` 失败（例如手续费账单因转出账户已不存在而 `addBill` 抛错），旧转账已丢失，新转账未创建，造成数据丢失。  
   复现要点：离线或账户被另一设备删除后，尝试编辑一笔转账；若转出账户不存在，手续费账单创建失败，整个更新过程中断且旧转账不复存在。  
   修复建议：将新旧转账的替换设计为可回滚的事务；或在调用 `addTransfer` 前预先验证所有依赖（账户存在、权限等），确保不会部分成功。

7. **P2（待确认）** 位置：`src/sync.ts` 新增的 `discardBaselessConflicts` 函数，及 `src/App.tsx` 中对应调用  
   现象：在同步完成后无条件调用 `discardBaselessConflicts()`，函数可能将本地存在但云端无对应基准的记录静默删除（注释“无云端基准的历史草稿…静默丢弃”）。这可能误删用户离线创建的、尚未上传的账单，造成离线补传队列数据丢失。  
   复现要点：离线时创建一笔账单，云端被重置清空；重新上线同步时，若该函数判断无云端基准，本地离线账单被丢弃。  
   修复建议：审查该函数具体实现，确认仅清理历史冲突占位数据而非所有无云端基准数据；建议增加确认机制或标记为“待核对”而非直接删除。

注：由于本次审查范围包含大量 UI 与脚本文件，以上问题主要聚焦于 `src/store.ts` 等核心业务逻辑；`src/domain/statistics-charts.ts` 新增的 `daily` 模式未见明显金额错误，连同其他 UI 文件本次未发现新的证据型问题。
