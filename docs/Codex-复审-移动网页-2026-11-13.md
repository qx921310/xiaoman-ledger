# 移动网页复审（2026-11-13）

## 范围与基准

- 用户目标是移动端网页，参考一木 APK 的记账业务与操作；不把 Android 原生专属能力缺失本身作为 Web 缺陷。
- 已提交基准 `8846cde`，对照上轮 `912a5b6` 的修复；复审时工作区的 `src/store.ts` 还有并行更新的未提交改动，不能将其当作已提交版本。
- 不操作生产或 staging；以下代码实验使用独立进程、虚构数据和内存 localStorage。未完成 APK 全量逐状态对比或 iOS Safari 真机验收。
- 结论：**本轮不通过上线验收**。旧问题有实质修复，但构建、余额流水、历史数据兼容、移动端功能和锁屏仍有问题。

## P1：阻断上线和数据正确性

### 1. 并行修改曾导致类型错误，复测已修复

`src/store.ts:687` 的待提交模板改动读取不存在的 `tr.number`；`:688` 将 `bookId` 传给不接受该参数的 `addTransfer`，还读取不存在的 `tr.bookId`。实际运行 `npm run check` 在 `tsc --noEmit` 退出 1，三条分别为 TS2339、TS2353、TS2339。转账模板金额字段实际是 `cost`。

审计过程中该未提交改动被继续更新：改用 `tr.cost` 并移除了错误字段；随后单独重跑 `npm run typecheck` 退出 0。因此这条作为过程记录，不再作为当前不通过项。这不表示模板所有行为已经正确，见第 8 项。建议补转账模板实际创建与执行测试：正确金额、当前/全部账本、账户失效及权限。

### 2. 定存改变期初余额，没有产生资金流水；并发时定存与账户可分开同步

`src/store.ts:501` 和 `:524` 直接增减资产 `openingBalance`；`src/balances.ts` 和 `src/domain/account-history.ts` 的流水没有定存。隔离复现：初始 1000，定存累加 500 后余额和期初均为 1500，但账户流水 0 条。账本清空会删除定存记录而保留资产（`server/server.mjs` 的清空规则），对应的期初修改不会自动冲回。

更关键：`src/domain/sync-v2-runner.ts` 的强关联表未包含定存关联账户。隔离 runner 复现：账户变更已有版本冲突、关联定存待推时，实际推送了 `fixedDeposit`，账户变更被拦下。两台设备基于同一个期初各增加定存时，账户版本会冲突；若简单选择一方余额，另一笔增量可能未体现，记录与余额不一致。

建议：先明确 APK“累加至账户余额”业务动作，再把余额变化设计成具备稳定身份和时间的资金事件/流水，或提供等价且可恢复的权威方案；定义删除、撤销、账本清空、冲突解决与余额重算语义。对两设备独立添加、失败重试、部分同步、切换账户、清空和备份恢复做端到端回归。仅把 asset 与定存加入批次关联不能单独解决并发增量覆盖。

### 3. `showBook: []` 旧数据的含义被原地改写

`src/domain/asset-scope.ts:14` 现在把空数组解释为全部账本隐藏；`912a5b6` 则仅在数组非空时按列表过滤，空数组等同未设置。旧版设置页还会在全选时写入空数组。没有发现数据版本或迁移步骤。

已有账户如果保存了旧版 `showBook: []`，升级后在具体账本的资产、记账账户选择和 OCR 确认中可能消失；数据不一定丢失，但用户可能无法使用账户。建议引入明确的版本标识/新字段区分旧“全部”和新“无”，覆盖本地持久化、云端和备份，不能无条件把所有新空数组转成全部。

### 4. 旧的三类实体仍可能被合并成副本

新建定存、愿望、智能分类已补 `ownerId`，针对新数据的测试通过；但旧版本创建的记录没有该字段，合并逻辑仍将本地缺属主视作 0，与云端附加属主不同后改号（`src/domain/sync-merge.ts:119`、`:132`）。隔离复现：从一条旧愿望移除 `ownerId` 后应用同一云端记录，数量从 1 变 2。

建议在不猜测账本与归属的前提下迁移可证明的历史身份，或保留待核对状态；对旧数据、双设备、重复拉取和冲突处理做回归。现有 `tests/fix-regressions.test.ts` 只覆盖新建且属主已存在的愿望。

### 5. 账号隔离后 PIN 在启动时可能直接跳过

`src/App.tsx:24` 在用户身份加载前以当前模块的空作用域执行 `hasPin()` 初始化 `locked`；直到 `:146` 用户加载后才设置账号作用域，没有依据新作用域重新上锁。若只存在账号键、无旧的无作用域键，刷新/冷启动时 `locked` 为 false，可直接进入。

此外，后台监听 effect 只依赖用户 ID；在当前会话设置 PIN 后若用户 ID 不变化，监听不会重新注册，切后台也可能不锁。旧无作用域 PIN 是否迁移也未见处理。建议在身份确定后按该账号决定是否解锁，监听状态变动，并覆盖冷启动、切账号、设置后立即切后台及旧 PIN 迁移。Web PIN 仍只能提供本机界面遮挡，不是本地数据加密。

### 6. 账本归属不明的新实体仍可绕过账本代次

定存、愿望和智能分类在“全部账本”时写 `bookId: undefined`（`src/store.ts:501`、`:539` 等）；服务端 `book-required` 列表没有这三种（`server/server.mjs:643`）。因此它们可被当成个人记录提交，不随账本清空的代次规则约束；同时列表未按当前账本过滤，不能据此认定这些实体具有完整的账本隔离语义。

建议先明确三者是个人数据还是账本数据；若属于账本，创建前必须选择具体账本并由服务端强制校验代次，旧数据不能静默猜归属；若属于个人，则调整产品文案与清空行为。测试离线创建、清空、不同账本及另一设备拉取。

## P2：移动网页实际体验和业务口径

### 7. 移动端记账没有接入智能分类、语音和保存模板入口

`src/features/add-bill.tsx:153` 在 ≤600px 返回独立移动端界面；移动备注的 `onChange` 只 `setRemark`（`:218`）。关键词规则、语音按钮和“存为模板”都位于该 `return` 之后的桌面分支（`:360`、`:363`、`:405`）。用户主要使用手机网页，因此不能以桌面逻辑存在就验收移动端功能。建议共用业务处理函数，并分别测试手机宽度手动输入、语音文本、人工改分类、保存/使用模板；iOS 浏览器能力要以实测为准。

### 8. 模板修复仍需完整验证

已提交 `8846cde` 的账单模板会在具体账本不同时拒绝，但“全部账本”仍允许通过，并由 `addBill` 使用当前账本 0；转账模板分支未进行同类检查。审计时未提交改动已增加账单模板账本和转账模板校验，但仍需验证“全部账本”下转账归属、只读账本、私有账户、已删除账户、0/非有限金额、转账账户相同、外币与手续费。不能把仅检查目标 ID 当作完整记账业务校验。

### 9. 资产走势标注了估算，但数学口径仍可能明显失真

上轮指出的问题未根治：`src/features/stats.tsx:61` 仍将不同币种账户数值直接相加，并以今天余额当所选历史区间末值，仅依据该区间账单反推；跨年用 `M/D` 分组可能合并同月日。新增“估算”提示是改善，但不应作为真实历史资产验收。建议用带时间与币种的资产事件及汇率计算，或明确不可计算的范围。

### 10. 现金兜底已处理失败状态，但并发首次创建未证明幂等

`src/App.tsx:175` 已正确排除 -1，单设备拉取失败时不再立刻补建。两台尚无资产的设备仍可能都先成功拉到空列表、再各自 `addAsset`；没有看到基于账号的稳定唯一键或服务端原子创建。建议使用两个独立会话控制同步屏障验证，并实现幂等创建；不要把此前顺序登录复验外推到并发。
